Read this way:

  * refine issues ZERO database queries in every case. Search, filters,
    sort and paging run over a set already in memory, which is the same
    fact as "changing a filter never calls the routing provider".
  * detours evaluated stays at 17 whether the table holds 8 restaurants
    or 5,008: the billed-call budget bounds it, not the corpus.
  * box candidates is capped at DISCOVERY_MAX_CANDIDATES (300), so the
    eligible set — and therefore the cached payload the warm path
    re-validates — cannot grow without limit.
  * the warm path is only slightly cheaper than the cold one at scale
    (70 ms vs 73 ms). Only the *selection* is cached; eligibility and
    availability are re-checked on every hit, by design, so a suspension
    takes effect immediately. With 258 restaurants that re-check is the
    bulk of the request.
  * the corridor query is a range scan on restaurants_position_index,
    reading 585 rows to return 281. No new index was warranted: a
    composite (status, verification_status, is_discoverable, latitude)
    index was built, measured, and REMOVED — it read 554 rows against
    the position index's 585, which is not a difference worth an index.
    The plan is recorded here so the next person does not repeat the
    experiment.
  * the restaurant_cuisines eager load is one query, not N. MySQL scans
    it rather than seeking when the id list is large relative to the
    table; at 5,011 rows that costs under a millisecond. It is a single
    query either way, which is the N+1 question.

The 5,000 scale rows are inserted by the measurement script, labelled
[PERF], and deleted before it returns. They are never partners.
